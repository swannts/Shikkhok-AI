# Shikkhok-AI Sync & Conflict Handling Strategies

This document defines how Shikkhok-AI handles synchronization and conflict resolution between offline clients (mobile) and the authoritative server.

## Overview
Shikkhok-AI employs an offline-first architecture where mutations are queued locally and synchronized with the API when connectivity is restored. To prevent duplicated writes or destructive overwrites, the system intentionally uses specific conflict handling strategies rather than defaulting to arbitrary "last-write-wins" for all entities.

The sync subsystem relies on `SyncEventRepository` to enforce idempotency. Each operation receives a unique `operationId` generated by the client. The server tracks these IDs and prevents re-execution of previously applied or currently processing operations.

## Data Authority & Strategies

### 1. Progress Metrics (Merge / Additive)
**Entity Types:** `lesson_progress`, `chapter_progress`, `practice_attempt`
**Strategy:** Server Authority & Additive Merge
- **Reasoning:** Learning progress is additive. A student practicing offline should have their progress merged into their total lifetime progress. If a client sends an update, the server compares the new metric with its existing state and accepts the higher value (e.g., maximum score, maximum progress percentage).
- **Implementation Details:** The backend service (e.g. `ProgressService`, `PracticeService`) checks if the submitted payload is an improvement before updating. It never allows a client's 50% offline progress to overwrite a server's known 80% progress.

### 2. Study Plans (Last-Write-Wins with Timestamp)
**Entity Types:** `study_plan`
**Strategy:** Last-Write-Wins (LWW) based on Client Timestamp
- **Reasoning:** Study plans are mutable documents representing a student's current intent. They can be overwritten.
- **Implementation Details:** The server accepts the client's payload if the `updatedAt` timestamp of the mutation is newer than the server's record.

### 3. Notifications (Idempotent State)
**Entity Types:** `notification`
**Strategy:** Idempotent Server Authority
- **Reasoning:** Notifications only flow from unread to read.
- **Implementation Details:** If a client marks a notification as read, it stays read. Duplicate sync operations for `NOTIFICATION_MARK_READ` are safely ignored by returning success idempotently.

### 4. Conversations & Tutor Messages (Append-Only)
**Entity Types:** `tutor_message`
**Strategy:** Append-Only
- **Reasoning:** A conversation is a ledger. Messages cannot be mutated after creation.
- **Implementation Details:** (Note: Tutor is currently strictly online, but if offline messaging is added, it will follow strict append-only rules using local IDs mapped to server IDs).

## Safe Replays
The Sync API (`POST /api/v1/sync/me/batches`) allows safe replay of batches. If a mobile client loses its internet connection right after sending a batch but before receiving the HTTP 200 OK, it will resend the batch later.

The `SyncService` handles this by checking the `sync_events` collection:
1. If `operationId` is `APPLIED`, the server skips execution and returns the cached result.
2. If `operationId` is `PROCESSING`, the server skips execution and returns a processing status.
3. If `operationId` is `FAILED`, the server allows a retry (claiming it for processing) provided it was a retryable failure (e.g. network glitch rather than a validation error).
